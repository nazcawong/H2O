# 取捨原則

H2O 不是「另造一門完全不同的語言」。正確態度是：把 1987–1990 年委員會真正想保住的少數核心思想留下，把三十多年累積的歷史包袱、不一致預設與工程摩擦清掉。

社群 2025 年 State of Haskell 調查（2026 年官方整理）反覆指向同一批痛點：`String`、紀錄系統、預設惰性、Prelude 部分函數、擴充爆炸。這些不是 Haskell 思想錯了，而是 1990 年的工程選擇在 2026 年已成為稅負。

## 總則

**留下「能用類型說清楚、能用等式推理」的一切；丟掉「靠歷史慣例、部分函數、預設惰性與擴充開關才能寫日常程式」的一切。**

Haskell 值得重寫的部分，從來不是語法糖或 GHC 擴充清單，而是：純度、精確資料模型、以及把副作用趕出核心的那股固執。其餘大多是可以、也應該換掉的工程選擇。

真正決定成敗的，往往是**必須新增、且不能再用擴充模擬的能力**。現有 GHC 已在實驗其中一部分（線性型別、Dependent Haskell 路線圖），但重寫時應把它們做成語言核心，而不是再疊一層 pragma。

## 新增規則

> 新增的東西必須減少擴充數量，而不是再製造一批擴充。

檢驗方式：

- 這件事若做成 `LANGUAGE` pragma，以後還會不會再長出三個相關 pragma？若會，它不該是擴充。
- 這件事是否讓日常程式**少寫**特例、少開開關、少依賴歷史慣例？若否，它不該進核心。
- 這件事是否能用 Core 已有的抽象編碼，而不損害推導與錯誤訊息？若能，它該是函式庫或選配層。

## 三層判斷

每個機制只進其中一層：

1. **必須保留**——沒有它就不再是 Haskell 思想的後繼。
2. **應捨棄或翻轉預設**——1990 年的工程選擇，2026 年的稅。
3. **宜重設計而非直接丟掉**——有價值，原樣搬會把舊病一起帶走。

「應新增」另見 [04-must-add.md](04-must-add.md)。選配與禁止見 [06-optional.md](06-optional.md)、[07-do-not-add.md](07-do-not-add.md)。

## 表面可讀性

語義跟 Haskell；表面跟 Haskell 無關。噪聲標準見 [11-readability.md](11-readability.md)：

- 語法噪聲：縮排、英語 `and`/`or`/`not`、條件無括號、沒有 `;`、沒有區塊 `{}`。
- 概念噪聲：一件事一種寫法（`h2ofmt`）；效應出現在類型上；`.` 只做欄位與模組。
- 資料流：多步只用 `|>`。

## 成功標準

H2O 算做成，當且僅當：

- 多數應用只需 Core 報告，不必列擴充。
- 效應可組合、可替換處理器，不必先學 monad transformer 堆疊。
- 紀錄可擴充、欄位不污染頂層；文字預設是 Unicode，不是 `[Char]`。
- 預設程式的空間行為可預測；無限結構仍寫得出來。
- 非法狀態能用類型表示出來——含資源生命週期與（可選的）索引不變式。
- 診斷以程式設計師詞彙為中心，而不是編譯器內部狀態。
- 讀程式時先看到名字與資料流，而不是符號；同一件事只有一種寫法。

內容定址、精細型別、完整證明都是加分，不是定義「這還算不算 Haskell 思想的後繼」。
