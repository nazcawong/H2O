# 不應保留：預設值與歷史債務

這些不是「Haskell 思想錯了」，而是 **1990 年的工程選擇在 2026 年已成為稅負**。重寫時應直接翻轉預設，或從語言核心拿掉。

社群調查裡最集中、也最可執行的幾條正是：`Text` 進 `base`、紀錄預設改成點語法且無頂層選擇器、拿掉惰性 I/O、Prelude 去掉部分函數、停止無節制加擴充並考慮新 Language Report。

| 項目 | 為何不留 | 較合理的新預設 |
|---|---|---|
| `type String = [Char]` | 鏈結串列字元幾乎是最差的文字表示；`base` 全用 `String`，新手與函式庫都跟著錯 | 預設 `Text`（Unicode 文字）與 `ByteString`（位元組）；`[Char]` 僅作教學別名 |
| 全面預設惰性 | 空間洩漏、難以推論記憶體、部署焦慮；調查中反覆出現 | **嚴格為預設**，惰性需顯式標註（或只對串流／無限結構開放） |
| 經典 record | 欄位選擇器污染頂層命名空間、同名欄位衝突、沒有一等 record、更新語法弱 | 列型別（row types）或內建結構化記錄 + `.` 語法；無自動頂層選擇器 |
| Prelude 部分函數 | `head`、`tail`、`(!!)`、`read` 類型謊稱總是成功 | 預設安全 Prelude：`NonEmpty`、`Maybe`／`Either`，部分函數放進明確模組 |
| 數以百計的 `LANGUAGE` 擴充 | 語言變成「GHC 方言集合」；學習曲線與可攜性都差 | 一份精簡、穩定的語言報告；進階能力分層（Core / Typed / Systems） |
| 惰性 I/O | 資源生命週期與求值順序糾纏，實務上幾乎一律避開 | 嚴格、有範圍的資源管理（bracket／線性／能力型效應） |
| 以 monad transformer 堆疊當「官方效應故事」 | 可組但難學、難除錯、效能與推論都痛苦 | 代數效應或能力系統作一等機制；Monad 留下當編碼，而非唯一介面 |
| orphan instance 作為常態 | 全域重載變得不可預測 | 實例與型別／類別同模組為預設；orphan 需顯式、可審計 |
| 模組系統過簡 | 可見性幾乎只靠 export list；抽象資料型別要靠慣例 | 真正的模組私有、分層可見性、較清楚的介面／實作分離 |

## 翻轉預設時的相容態度

H2O 沒有「載入舊 Haskell 原始碼就能編譯」的義務。目標是思想連續，不是語法連續。

遷移若要做，應是明確的工具與子集，而不是在核心裡同時維持兩套預設。兩套預設等於又一種擴充。
