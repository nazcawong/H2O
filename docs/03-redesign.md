# 不宜直接丟掉、但必須重設計

這些機制有價值，原樣搬過去會把舊病一起帶走。

## 1. 惰性

保留「可惰性」，放棄「處處惰性」。

- 嚴格資料（相當於預設 `StrictData`）應是常態。
- 惰性列表／串流作為明確型別存在。
- 仍能寫無限結構，但預設程式的空間行為可預測。
- 融合優化（rewrite rules、`foldr`／`build`）作為可宣告的優化規則留下，掛在惰性／串流型別上，而不是當成全語言的隱式救命稻草。

## 2. 類型類階層

`Functor` → `Applicative` → `Monad` 這條線是對的，應保留並讓定律可檢查。

要改的是：

- `Num` 過寬——不該同時代表算術、字面值與轉換。
- 歷史命名不一致（`return`／`fmap`／`map`）。
- 「為了推導開啟一堆危險擴充」的文化。orphan、overlapping 不是日常工具。

Monad 是效應的一種編碼，不是效應的官方故事。見 [04-must-add.md](04-must-add.md)。

## 3. 類型級程式與依賴類型

現況是 TypeFamilies、DataKinds、GADT 疊出來的「準依賴類型」：擴充多、錯誤訊息差。

重寫時較乾淨的路有兩條，H2O 選的是**分層**，不是再模擬：

- 把穩定的類型級功能收進 Core／Typed（對齊 GHC2024 已開始收斂的那部分）。
- 像 Idris 那樣把依賴類型做成可選、有總性檢查的一層，而不是再用三十個擴充模擬。

務實分層見 [04-must-add.md](04-must-add.md) 第 4 節。完整證明助理模式不進核心，見 [06-optional.md](06-optional.md)。

## 4. 編譯器與工具鏈經驗

GHC 的優化與重寫規則是資產，應保留「可被程式設計師宣告的優化規則」這個想法。

應丟掉的是：

- 過長編譯時間被當成常態
- 錯誤訊息以編譯器內部詞彙為中心
- 語言伺服器記憶體與穩定性問題

語言重寫若不同時重做診斷，只是換一套同樣難用的語法。增量編譯是設計約束，不是事後優化。見 [05-engineering.md](05-engineering.md)。

## 5. 套件與預設函式庫

「有一個小而驕傲的 `base`」這個目標要留；現況那個混雜便利函數與部分操作的 `base` 不要留。

文字、容器、效應、解析，預設就該是現代、總性較高的 API：

- `Text`／`ByteString` 一等
- 容器嚴格；串流惰性且獨立
- `NonEmpty`、`Either` 錯誤通道從第一天就是預設
- 數值塔重新設計
