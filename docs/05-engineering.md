# 應新增的工程層能力

這些不是「理論上漂亮」，而是工業使用的缺口。語言重寫若不同時做這些，新語言仍難用。

## 診斷與除錯

- 錯誤訊息以程式設計師詞彙為中心，而不是 Core／constraint solver 內部狀態。
- 例外預設帶穩定回溯；惰性若仍存在，求值棧與詞法棧要分開呈現。
- 類型洞（typed holes）、有效洞填充、逐步細化作為語言互動模型，而不是編輯器外掛偶然能用。

依賴類型與效應列會讓診斷更難，不是更容易。診斷必須是一等公民，與類型系統一起設計。

## 模組與封裝

- 介面與實作分離（接近 Clean／ML）。Clean 那套分離檔值得參考，但不必然照搬。
- 建構子可真正私有，不必只靠 export list 慣例。
- 一等模組或至少可抽象的簽名，避免「一千行 Types.hs」。
- 實例與型別／類別同模組為預設；orphan 需顯式、可審計。

## 元程式

- 以**類型安全的引用／報價**取代 Template Haskell 的主路徑。
- 衛生、階段區分（cross-stage persistence）寫進語言，而不是再一套準系統。
- 宏系統不得先於類型系統：先有可靠的類型與階段，再談語法擴充。

## 格式

- `h2ofmt` 是唯一風格，對齊 `gofmt`：不討論對齊、引號、尾逗號。
- 一種呼叫、一種管線、一種區塊。格式化工具刪掉第二種寫法，而不是提供選項。

## 編譯與身分

- 增量編譯為設計約束，不是事後優化。
- 可考慮內容定址（Unison）：函數身分是雜湊，不是檔名＋模組路徑，減少依賴地獄。這是加分，不是定義特徵。
- 穩定 ABI 與跨編譯（原生／WASM）作為後端契約，而不是「編譯器碰巧能出某後端」。
- 可被程式設計師宣告的優化規則留下（GHC rewrite rules 的思想）。

## 標準庫契約

- `Text`／嚴格容器／`NonEmpty`／`Either` 錯誤通道從第一天就是預設。
- 屬性測試、黃金測試、最小反例進入標準工具鏈。
- 數值塔重新設計：不要再讓 `Num` 同時代表算術、字面值與轉換。
- 串流是標準效應，不是生態裡互相不相容的四套函式庫。
- `base` 保持小而驕傲：現代、總性較高，不含部分操作的便利陷阱。
